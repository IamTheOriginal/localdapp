# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Dapp Builder — a local-first, peer-to-peer, no-code Dapp builder. React 19 + TypeScript, Yjs (CRDT) for shared state, a member-verified WebRTC mesh for P2P sync (y-webrtc only for invite/lobby/relationship rooms), shadcn/ui (Base UI, not Radix) + Tailwind v4. **Code Apps are the only creation path** — the visual screen designer/renderer era is over; its leftovers should be removed on sight, not extended.

## Commands

- `npm run dev` — Vite dev server + signaling broker (`server/signaling.mjs`, the same one production uses; `npm run signaling` runs it alone; deployment story in `docs/DEPLOYMENT.md`)
- `npm run headless` — always-on keeper node (`server/headless.mjs`, needs Node ≥ 23.6; see Headless runtime below)
- `npm run build` — `tsc` then `vite build`
- `npm run typecheck` — `tsc --noEmit`
- `npm run lint` / `npm run lint:fix` — ESLint over `src/`; warnings are ratcheted via `--max-warnings` in package.json — fix or offset any warning you add, and lower the ratchet when you remove some
- `npm test` — Vitest, run once (`npm run test:watch` for watch mode)
- Run a single test file: `npx vitest run src/__tests__/<file>.test.ts`
- Tests live in `src/__tests__/`, environment `node` by default (`// @vitest-environment happy-dom` per file where DOM is needed, `fake-indexeddb` where IndexedDB is needed). `src/__tests__/setup.ts` repairs `localStorage` under happy-dom on Node ≥ 25 — don't work around broken storage per-test. Auth enforcement is asynchronous: wait with `whenAuthObserversIdle()` (auth.ts), never with a fixed sleep — a sleep races the scan under load, and a "nothing was reverted" assertion behind one cannot fail. Compare byte arrays with `helpers/bytes.ts::expectSameBytes` (`toEqual` on a typed array costs seconds).
- `npm run smoke:keeper` — boots the real keeper entry point against a temp directory (CI runs it on Node 25)
- CI (`.github/workflows/ci.yml`) runs `tsc --noEmit`, `lint`, `test` and `build` on Node 22 and 25, plus the keeper smoke test on 25, on push/PR to `main` — match this locally before pushing. New files need `git add`: `git commit -a` skips them, which once left `main` importing modules that did not exist.

## Architecture

### Data model: Yjs documents, not a server

There is no backend. All state lives in Yjs CRDT documents, persisted locally via `y-indexeddb` and synced peer-to-peer. A dapp's data and source documents travel **only over the member mesh** (`blobRoomManager.ts`, see Member mesh below): a peer must prove a whitelisted member key before any document byte is exchanged — the room password alone grants nothing. `y-webrtc` (room ID + password, hands the doc to anyone holding it) is left for rooms whose other side is not a member by design: invite/lobby rooms and the relationship pairing/channel rooms. Never attach a `WebrtcProvider` to a dapp's data or source doc (`dappTransport.test.ts` enforces it). Every peer independently enforces invariants — there is no server-side authority to trust, so validation logic (see Auth below) runs identically on every honest client. `src/services/store/docs.ts` owns doc/provider/persistence lifecycle (root doc, per-dapp doc, per-dapp source doc, invite docs, lobby doc, relationship channel docs); `src/services/store/index.ts` re-exports the full store API assembled from the other `store/*.ts` modules — read it first to see the whole surface area.

A dapp is generally **two or three separate Yjs documents**, each with its own persistence:
1. **Dapp document** — metadata, members, schema (entities/fields, consumed by `$store`; a derived copy — the authoritative schema is the manifest's `entities` section, re-seeded via `syncManifestEntities` on install and manifest save), records.
2. **Source document** — the Code App's file map (`index.html`, `manifest.yaml`, ...). It rides the same member mesh as the dapp document (doc kind `source`), so approved members get it without a second invite secret.
3. **Relationship channel documents** (sharing feature) — see below.

### Auth model (`src/services/store/auth.ts`)

Records are Ed25519-signed by the writing device. `src/services/identity.ts` owns key custody: private keys are **non-extractable CryptoKeys in IndexedDB** (never plaintext in localStorage; legacy identities are migrated at startup, and identity export is removed by design). Signing call sites use `getSigningIdentity()`; `protocolCore.ts`'s `SigningIdentity.privateKey` accepts hex (Node twin, tests) or a `CryptoKey` (browser). An auth observer runs on every peer and asynchronously reverts: unsigned records, records signed by unknown/viewer/malformed keys, and records whose signature doesn't verify. The `members` Y.Map has its own baseline+signed-op protection (owner-signed adds, signed tombstone removals, timestamp precedence to prevent replay). A removed member loses access through the member-mesh whitelist: every honest device refuses its handshake and drops open sessions as soon as the removal syncs. Credential rotation (`store/rotation.ts`: owner-signed, per-member-encrypted `rekeys` entries, strictly increasing epoch) still exists and devices still follow existing entries, but it no longer runs automatically on removal/departure (`store/rotationPolicy.ts` — it split dapps whose members were offline). Everything owner-only is owner-signed and verified before use: members, invites (`writeSignedInvite`, signed tombstones, `uses` capped through members' `viaInvite`; lobbies and approvals act on `getVerifiedInvites` only), the Code App source (see Code Apps) — and checks read the observer's VERIFIED members (`getVerifiedMembers` / `getRole`), never the live map. The founder is pinned per device (`getFounder`); signed timestamps are monotonic (`timestampAfter`). Changes to the member list are resolved in an order-independent fixpoint (`scanAndRevertUnauthorizedMembers`), with signer authority judged from signed evidence (`createOwnerAuthorityLookup`: current verified owner, or a tombstone proving the key was an owner at that timestamp), never from the live map. A session starts from the members this device VERIFIED last time (`store/memberBaseline.ts`, persisted device-local; the keeper stores it in a file because Node's localStorage is volatile — `headless/deviceStateFile.ts`), and only the first sight of a dapp trusts the list as found. Never "fix" the remaining trust-on-first-use by rebuilding the list from the founder, and never delete a member for lack of a chain: entries are last-writer-wins, owners that edited each other's entry only carry each other's signature, and such a rebuild deletes them (tried and reverted 2026-09-18, `memberCrossSigned.test.ts`). Every failure of the baseline store falls back to the list as found, never to "delete what is unproven". Deletion needs PROOF of badness (no signature, a signature that does not verify, a signer known not to be an owner, a stamp that goes backwards, a superseding tombstone); an entry whose signature is fine but whose signer this device never verified is QUARANTINED instead — left in the document untouched, given no role and no mesh access here, its records not reverted (`getQuarantinedMembers`, `memberQuarantine.test.ts`). A self-signed unknown entry is still deleted. Any owner-signed touch of the entry resolves it. Invite lobbies: announces are signed (`store/lobbyAnnounce.ts`), the connection code is `connectionCode.ts` (8 digits, stretched, lobby-bound), the credential grant is signed (`store/accessGrant.ts`) — `approveLobbyDevice` is the single choke point and demands the proof itself. On the joining side a grant is never used straight away: `store/pendingGrant.ts` holds it until the person confirmed "approved by X — code N" (`ConfirmApprovalCard`), because a link holder can pose as an owner; headless devices decide through `setAccessGrantAutoConfirm` (the keeper: its verified operators), everything else waits for `decideGrant`. See `docs/security/THREAT_MODEL.md` for the full trust-boundary writeup and known residual risks (offline members miss rotations; pre-rotation members lack a stored `encPublicKey`) — read it before touching auth, signing, membership, or rotation code.

### Code Apps (`docs/code-apps/README.md`)

A Code App is a synced `index.html` run in a sandboxed, non-same-origin iframe (nonce-protected bridge, CSP blocks external scripts/network/frames/forms). Injected globals: `Dapp` (context/identity/role), `$data` (generic JSON KV in the dapp doc), `$store` (entity CRUD against the dapp schema, owner/editor-gated writes), `$router` (host-synced navigation driven by a `manifest.yaml` route list — `navigate()` only accepts declared routes), plus `$events`/`$actions` (manifest-declared bindings), `$contacts`/`$share` (channel shares — see relationship sharing), and `$files` (P2P file store, gated on `permissions.host.files`). The sandbox has no top-navigation or popup token: http(s) links go through the `ui.openLink` bridge call, which opens a new tab only after a host confirmation showing the address; relative links and `javascript:`/`data:` etc. are stripped. `$share.list/participants/close/leave` need `permissions.host.sharing` like `$share.open`, and close/leave ask the person first. **The source is owner-sealed** (`src/services/store/sourceSeal.ts`): every write through `store/source.ts` re-seals (owner-signed `path → SHA-256`); the runtime (`useRunnableCodeApp`) and every host-side manifest reader that grants something (`getRunnableCodeAppFile` — permissions, channel shares, app roles) use the sealed snapshot, the editor uses the live doc. A seal survives the loss of its signer: each device remembers the last seal it verified (device-local via `deviceStore.ts`) and keeps accepting exactly that one after its signer left; a device with no seal history runs a seal by a key it cannot place as `legacy`, like no seal; owner devices re-sign such seals (capped, never their own). Enforcement was off 2026-09-18 to 2026-09-22 and is back on; `SOURCE_SEAL_POLICY.enforce` stays as an emergency switch with both settings under test. Never re-seal on a digest mismatch (the 2026-09-18 re-seal war between owner devices). Never compare the seal's `dappId` with the local id: dapp ids are device-local (each join picks its own UUID), and that check made every other device's seal read as "no seal" — the 2026-09-23 restore loop between the keeper and a browser. Restores are capped (one per 30 s per dapp) and only re-seal when the files are unchanged. An owner device signs only content IT verified — never the live files because a seal looks repairable (that let a member's throwaway-key seal be signed by the keeper). Seals v2 are bound to the dapp's founder-signed, per-device-pinned genesis id (`store/dappGenesis.ts`); v1 seals still count until a device verified a v2 one. Never write the source doc's `files` map outside `source.ts`, and never read `manifest.yaml` for a permission decision through `getCodeAppFile`. Runtime lives in `src/services/codeAppRuntime.ts` + `src/components/code-app/CodeAppRuntime.tsx`; manifest parsing/validation in `src/services/codeAppManifest.ts`. Manifests are **YAML** (`manifest.yaml`, YAML 1.2 core schema via the `yaml` package — JSON syntax still parses since YAML is a superset; there is no `manifest.json`).

### Starters (`public/starters/`, `src/services/store/starters.ts`)

Starters are **content, not code**: static template bundles under `public/starters/<id>/` (`index.html` + `manifest.yaml`, whose `entities` section carries the schema — there is no separate schema.json — plus any linked files the catalog entry lists under `files`: stylesheets, classic scripts, vendored libraries, SVGs, in subdirectories if wanted) listed in `public/starters/index.json`, fetched at runtime by `StarterGallery` and installed via the generic `fetchStarterCatalog`/`fetchStarterDefinition`/`createStarterDapp` pipeline in `src/services/store/starters.ts`. Every definition passes `validateStarterDefinition` (manifest parse incl. entities + `validateCodeAppFiles`) at install time — malformed content fails closed. To add or change a starter, edit the static files only; never put starter- or use-case-specific logic in `src/`. Tests load the shipped files from disk via `src/__tests__/helpers/starterFixtures.ts`, so content defects fail CI (including a catalog `files` list that disagrees with the files on disk). `todo-list` is the reference multi-file starter: vanilla JS split into `styles.css` + `app/*.js` sharing a `Todo` global — Code Apps have no ES modules and no build step, so split files are classic scripts in document order. Keep starters framework-free unless told otherwise.

### GitHub-sourced dapps (`src/services/githubSource.ts`, `src/services/store/githubOrigin.ts`)

A dapp can be created from a public GitHub folder (New Dapp → Add from GitHub). `githubSource.ts` is plain-fetch transport + validation (api.github.com for commit/tree, raw.githubusercontent.com at the pinned commit, every file verified against its git blob SHA); `store/githubOrigin.ts` installs the snapshot and keeps the origin (repo/ref/folder/commit/fingerprint) in the source doc's `origin` map — synced, peer-writable, validated on read, and only ever an *offer* to review. Update detection is device-local and owner-only (`githubUpdateState.ts` in localStorage + `useGithubUpdate`, ≤ 1 request per dapp per 6 h, red dot on “Dapp settings”); applying is an explicit owner action in `GithubSourceCard` (`applyGithubUpdate`, owner-gated, same repo location only). **Never auto-apply and never call the check from `src/headless/`, `store/*` or automations** — a test enforces it. User docs: `docs/code-apps/README.md` → “Adding a dapp from GitHub”.

### `$db` read model (`docs/plans/2026-08-24-read-model.md`)

`src/services/store/readModel.ts`: an in-memory, per-dapp index over the auth observer's verified record set (auth.ts emits accepted upserts/deletions per scan; nothing is persisted — the earlier IndexedDB projection `dapp-projection-<id>` is deleted on sight). Code Apps declare sortable fields in the manifest (`db.indexes`) and read via `$db.query/get/count` with cursor pagination and structured match filters; subscriptions are invalidation-only. Never index unverified doc state, never add a write surface. `$store` stays the write path and the canonical read; `$db` may trail it by one scan debounce.

### Member mesh — live sync + whitelist (`src/services/blobRoomManager.ts`, `blobProtocol.ts`)

One simple-peer mesh per dapp, discovered through the signaling broker under a topic derived from the dapp's room credentials (`blob-v1-…`; the name predates live sync), signaling payloads AES-GCM-encrypted. All channels of a device share ONE broker socket PER CONFIGURED ENDPOINT (each channel is a topic subscription on each socket) — never open a socket per dapp: dapps × tabs × devices behind one public IP runs into the broker proxy's per-IP connection limit and the newest channel silently finds no peers. Every configured endpoint is held at the SAME TIME, never one after the other: a broker only relays between its own subscribers, so a device that rotated to the next URL after a drop stopped meeting everyone still on the first one. Announces and signals go out on every open link and the copies that come back are dropped by an envelope id inside the ciphertext (`alreadySeen`), so a peer is dialed exactly once. The endpoint list is per device — the build default, or Settings → Signaling (`services/signalingConfig.ts`, localStorage, never synced, never in a document or an invite); `signalingEndpoints()` is the plug point for a future per-dapp list. Every data channel becomes a `BlobPeerSession` whose Ed25519 hello/proof handshake is **the peer whitelist**: `isTrustedBlobPeer` accepts current members, or — while a fresh joiner's members map is still empty — only the owner key named in its access grant (`store/accessGrant.ts`). A member that lost its copy can wait in an invite lobby again: owners see a rejoin request (`store/lobbyPeers.ts`), and `approveLobbyDevice` re-sends credentials encrypted to the member's STORED `encPublicKey` without touching its entry — never trust the key announced in a lobby for an existing member. Refused devices get a 2-minute redial cooldown; open sessions are dropped when the members map stops trusting their key. Live sync: local doc updates are pushed to every ready session and relayed onward (duplicates are Yjs no-ops, which ends the relay), updates too large for one frame become a `poke` that makes the receiver pull, and both sides pull the diff against their state vector on connect. Remote updates carry a `MeshOrigin` transaction origin. Presence (`meshPresence.ts`, leaf module) is the set of verified ready sessions — there is no awareness protocol on dapp docs. `docs.ts::getDappDoc` starts the mesh via dynamic import when credentials exist (`setMeshAutoConnect(false)` in the keeper, which sequences it after file persistence). All devices of a dapp must run a mesh-sync build — older builds only speak y-webrtc for live changes.

### Blob store / file sync (`docs/plans/2026-08-24-blob-store.md`)

Files sync Syncthing-style: signed `FileRecord` metadata in the dapp doc's `files` map (auth-observer-validated, tombstone deletion, ≤32 KB inline thumbnails are the only inline binary), content in a content-addressed chunk store (`src/services/blobStore.ts`, IndexedDB chunks — a legacy OPFS directory is drained once on first open — 256 KiB chunks, pin/LRU-GC). Transfer runs over the member mesh (above; transport-abstract protocol in `blobProtocol.ts`): membership is proven with an Ed25519 handshake before any chunk is served — room credentials alone never grant blob access — and every chunk is hash-verified on receipt. The mesh topic derives from the dapp's credentials, so credential rotation carries over. UI at `/dapp/:id/files`; Code Apps get `$files` behind `permissions.host.files`. Per-dapp replication is `onDemand` (default) or `pinAll` (toggle on the Files page; the headless keeper sets it). Device-local cleanup (`src/services/blobCleanup.ts`, policy in localStorage, never synced): age + LRU-size eviction of unpinned copies only, scheduled from `App.tsx`, configured under Settings → Local data — own uploads and pin-all dapps stay pinned and are never evicted while a live file record references them; content of deleted file records is unpinned (`releaseBlobsOfDeletedFiles`), and the keeper also sweeps content no dapp references (`sweepUnreferencedBlobs`). Record and file tombstones expire after 90 days on owner devices (`store/historyCompaction.ts`, member tombstones never), and a device puts its own records back when a peer replaced a collection container (`store/recordContainerMerge.ts`). Never put blob bytes into a Yjs type.

### Plugins — removed

The iframe plugin system (dapp-plugin.js SDK, `PluginScreenView`) was removed with the visual era. Don't resurrect it; Code Apps are the extension mechanism.

### Relationship sharing / channel rooms (`docs/plans/2026-08-12-relationship-sharing.md`, `docs/plans/2026-08-20-code-app-platform-expansion.md`)

Subsystem (`src/services/store/people.ts`, `relationships.ts`, `channelRegistry.ts`, `channelShares.ts`, `contacts.ts`, `pendingShareInvites.ts`, `directBindings.ts`; runtimes in `src/services/browserRelationshipRuntime.ts`, `channelBindingRuntime.ts`, `sharingRuntime.ts`, `relationshipChannelControl.ts`) for sharing a *subset* of a dapp's data/events with specific people without adding them to the full dapp room. Key invariants: the global people/relationship catalog is local-only (never attached to a `WebrtcProvider`); each `(relationship, dapp)` pair gets its own randomly-keyed channel room, so unrelated recipients never share a room or see each other; only manifest-declared channel-share events are materialized into channel docs — a confidentiality boundary, not just a UI filter; incoming share offers are staged as `PendingShareInvite` and installed only on explicit user accept (never auto-install). `$share.open` is non-blocking and idempotent per contact: it reuses a contact's existing non-revoked channel for the same `shareId` instead of re-inviting, and declared channel-share events published while the share is still pending queue durably in that channel doc (the sender's own signed writes only — inbound processing stays gated on activation). The entity schema travels inside the manifest's `entities` section, signed with the files — the manifest is its only carrier (the bundle-level `schema` side-channel was removed). Pairing invites are compact seed codes (`dapp://invite/pair/…`, 32-byte seed; lobby credentials HKDF-derived; the signed inviter identity is announced inside the code-gated lobby and verified against the derivation) with hosted invites and joining sessions persisted in the root doc and resumed at startup, so pairing survives closed dialogs and restarts. Read the plan docs' security-invariant sections before extending this code; it's more security-sensitive than typical CRUD.

The relationship *control* capability (the pairing control room's credentials) lives in `store/relationships.ts` next to the relationship rows; the former `relationshipCapabilities.ts` module and the received-channel-capability map were removed as dead weight. The live channel install path is `relationshipChannelControl.ts::acceptChannelShareOffer` → `channelRegistry.ts::installChannelDescriptor` (the legacy auto-installing `channel-offer` receiver was removed).

### `$store` bridge (`src/services/codeAppStoreBridge.ts`)

The visual-era script sandbox (`scriptSandbox.ts`) was deleted; what survives is the `$store` RPC bridge — collection-name resolution + CRUD dispatch for Code App postMessage requests. The host CSP has no `'unsafe-eval'`; don't reintroduce an eval path anywhere (srcdoc Code App iframes inherit the host CSP). `'unsafe-inline'` in `script-src` is load-bearing: it is what lets Code App inline scripts run.

### Automations (`src/automations/`)

A host-agnostic automation engine (cron triggers + templated record steps) with store support (`store/automations.ts`). Cron rules are executed by the headless runtime (see below), which is the only importer — the engine never enters the browser bundle. Event triggers and `publish-event` steps were removed (they need a Code App host); re-add them together with the host, not before. No UI yet — don't ship UI features that depend on it without wiring + tests.

### Headless runtime / keeper node (`src/headless/`, `docs/HEADLESS.md`)

`npm run headless` (entry `server/headless.mjs`, Node ≥ 23.6 native type stripping — no build step; Dockerfile.headless for containers) runs an always-on peer that reuses the browser store stack under Node: `env.ts` installs shims (fake-indexeddb, localStorage polyfill, node-datachannel WebRTC injected via `signalingConfig.setRuntimeNetworkOverrides` — one hook covers the remaining y-webrtc providers and the member mesh), while durability is layered beside the volatile shims: `filePersistence.ts` (snapshot+log per Yjs doc), `identityFile.ts` (device keypair in `identity.json`, re-seeded into localStorage each boot), `blobBackend.ts` (fs chunk store via `blobStore.configureSharedBlobStoreBackend`). `runtime.ts` orchestrates catalog-driven connects, pin-all blob replication, chunked doc catch-up, and the cron automation ticker; `control.ts` is the token-guarded HTTP control surface (loopback by default). Because the real store modules run, all auth/rotation/membership invariants hold identically — the keeper cannot grant itself access (design record: `docs/plans/2026-08-26-headless-runtime.md`; manual E2E: `scripts/headless-owner-sim.mjs`). Keep `src/headless/` Node-only and never import it from browser code.

### Frontend structure

- `src/types.ts` — core types (`FieldDef`, `EntityDef`, `DappConfig`, `DeviceIdentity`, `CodeAppManifest`, `ChannelShare`, etc.) — the shared vocabulary; check here before adding a parallel type elsewhere.
- `src/hooks/useYjs.ts` — Yjs doc hooks, verified-peer presence (`usePeers`), role management; most pages/components consume store state through hooks here (plus `useSharing.ts`/`useRelationships.ts`) rather than touching `store/*` directly.
- `src/pages/` — routed pages: `HomePage`, `PeoplePage` (contacts/relationships/pending invites), `DappPage` (Code App runtime shell, incl. `/app/*` and `/full/*` routes), `CodeAppEditorPage`, `ThemePage`, `DappSettingsPage`, `SettingsPage`, plus the OS-launch landing pages `ShareTargetPage` (`/share-target`) and `OpenFilePage` (`/open-file`, `.dapp` files via `file_handlers` — format in `src/services/dappFile.ts`).
- `src/components/` — shared UI; `ui/*` is shadcn-generated, `code-app/*`, `settings/*`, `sharing/*`, `home/*` are feature-scoped.
- Home layout (`src/services/store/homeLayout.ts`, `useHomeLayout`/`useDappsList` in `useYjs.ts`, `src/hooks/useGridDrag.ts`, `src/components/home/*`) — a saved manual dapp order plus one level of folders. Position lives on the catalog item (`sortOrder`, integer string spaced by 1024, optional `folderId`), folders in the root map `dappFolders`; a move is a per-field `set` — never delete and re-insert a catalog item, it holds the room credentials. **The order is per device**: the root doc has no network provider, so layout never syncs between devices (two tabs only merge through IndexedDB on reload). Folders with fewer than two active dapps dissolve on read (`buildHomeLayout`) and are pruned by the next layout write, so leave / delete / keeper paths need no folder hooks. Drag and drop is native Pointer Events (no DnD library; cards must not set `touch-action: none`); the "⋯" Move menu is the keyboard/screen-reader path and must keep parity with every drag gesture.
- `src/i18n/` — minimal key-based i18n (`en` pass-through + `de` dictionary); shell strings added to the UI must get a `de` entry (a test enforces coverage of required shell keys).

### Conventions

- File naming: PascalCase components, camelCase services/hooks.
- `@/` import alias maps to `src/`.
- shadcn/ui components use Base UI (not Radix); trigger components follow the `render` prop pattern.
- Never `await persistence.whenSynced` bare: y-indexeddb's promise never settles when IndexedDB cannot be opened. Use `store/storageHealth.ts` — `whenLocalCopyLoaded` (carry on in memory) or `requireLocalCopyLoaded` (a decision depends on the loaded state: leaving, exporting). The same module feeds the shell's storage warning (unavailable storage, failed writes).
- Deleting a dapp's local data goes through `purgeDappLocalResources` only: it stops the mesh first, blocks `getDappDoc` from recreating the document meanwhile, tears down the auth / rekey observers and keeps blobs another dapp still lists (`store/blobReferences.ts` — also the check before ANY `deleteBlob`).
- Store-layer functions take an optional `doc: Y.Doc` parameter defaulting to the relevant getter (`getRootDoc()`/`getDappDoc()`) — follow this pattern for new store functions so they stay testable without a live provider.
- The shell opens only dapps this device OWNS at startup (`watchedAtStartup` in `useRequestsInbox.ts`, from the verified role docs.ts caches in the catalog entry's `role`); everything else loads when it is opened. Don't add shell-level code that walks the catalog and calls `getDappDoc` on every entry — each call loads a document and brings up a mesh.
- React state is for ephemeral UI-only state; anything collaborative goes in a Yjs shared type.
- Record storage (`src/services/store/recordContainers.ts`): every new collection is `compact` (Y.Map keyed by record id, one plain-JSON value per record — whole-record LWW, matching the signing model). The legacy `fields` shape (Y.Array of per-field Y.Maps) is no longer created; owner devices convert existing ones on open (`data.ts::migrateLegacyCollections`). The manifest's `storage.recordFormat` is parsed for compatibility but ignored. Readers stay container-agnostic (`containerRecords`) until the legacy branch is deleted after the migration window.
- Keep the core generic: no use-case-specific logic (shopping lists, expenses, ...) in `src/` outside starter template data.
