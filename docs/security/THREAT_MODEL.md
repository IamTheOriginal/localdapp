# Dapp Builder Security Threat Model

## Scope

Dapp Builder is a local-first P2P app builder. A dapp's documents sync over a WebRTC member mesh whose Ed25519 handshake admits only devices that prove a member key (see "Member mesh" below); the room password alone grants nothing. y-webrtc rooms, protected by room passwords only, are left for invite lobbies and relationship pairing/channel rooms. There is no central server-side authority, so every honest peer independently validates shared CRDT state.

## Trust boundaries

- **Outside attacker without room credentials:** cannot find the dapp's mesh topic or decrypt its signaling, and would fail the member handshake anyway.
- **Admitted peer with room credentials:** can write to the shared Yjs document, so all important invariants must be re-validated locally by every honest peer.
- **Owner device:** root of trust for membership changes and invite approval.
- **Browser origin:** private identity keys still live in browser storage; same-origin XSS remains a high-impact risk.

## Enforced now

### Record writes

Records are Ed25519 signed. Honest peers reject records that are:

- unsigned,
- signed by unknown keys,
- signed by a viewer or malformed role,
- signed with a signature that does not verify against `_signedBy`.

The auth observer performs async signature verification and reverts invalid records. Reverts are bound to full record snapshots to avoid deleting a later valid state after async verification returns.

**Tombstones expire after 90 days** (2026-09-22, `store/historyCompaction.ts`): record and file tombstones used to be kept for ever. Owner devices now drop, when they open a dapp, every record/file tombstone older than 90 days whose record is not in the document, plus `rekeys` entries below the current epoch − 1 (a device follows the newest entry addressed to it). Every auth observer lets a vanished tombstone go instead of restoring it once it is older than 83 days (a week of slack for clocks that run behind the pruner) and its record is not in the document — a tombstone removed together with a replayed copy of its record is still restored and the copy reverted. Anyone can remove an expired tombstone (a Yjs delete carries no author); that is equivalent to the owner pruning it. **Accepted trade-off:** a deletion is enforced for 90 days, not for ever. A device that was offline for longer and still holds the record comes back, receives the deletion without its tombstone, and its auth observer restores the record it last verified — the record is back for everyone; likewise a member that kept the old signed record can re-insert it once the tombstone is gone. Neither gains more than a writer already has (writing the record again). Member tombstones are never compacted: they carry the former-writer proof (`formerRole` / `formerEntry`) without which every later verification would revert what a removed member wrote.

**Collection containers are merged, not lost** (2026-09-22, `store/recordContainerMerge.ts`): a collection is a last-writer-wins value of the `data` map, so two members creating the same collection concurrently (or a write racing the owner's legacy-to-compact conversion) used to orphan one container with its records. Owner devices now create every manifest-declared collection's container when the schema is seeded, and every device puts its OWN signed records from a container that was replaced back into the surviving one, unchanged — the auth observer judges them as before. Records of an author whose devices never come back stay lost with the container they were in.

### Membership changes

The `members` map is protected by an auth observer baseline plus owner-signed operations:

- direct role edits by editors are restored,
- new members must be owner-signed,
- payload `publicKey` must match the Yjs map key,
- removals use signed tombstones,
- founding owner removal is rejected,
- timestamp precedence prevents replaying an old signed add over a newer removal and prevents stale tombstones from deleting newer re-adds.

Existing unsigned dapps are handled by a first-non-empty legacy baseline so loading older dapps does not brick membership (tombstones present at baseline capture are trusted alongside it).

**Voluntary departure ("leave dapp", 2026-08):** a member tombstone is also accepted when it is signed by the removed key itself — a member may always remove *themselves*, never others (`leaveDappMembership` + `isAuthorizedMemberRemoval`). The founding owner cannot leave (delete instead), so a deterministic single rotator would always exist. Since 2026-09-17 nothing rotates on a departure (see "Room password rotation"): the departed key fails the member-mesh handshake on every honest device as soon as the tombstone has synced, which is what ends its access. The leaver's device keeps a disconnected local archive (catalog credentials scrubbed, providers torn down; doc + persistence retained).

Residual risk of departures:

- **Leaving while offline** never delivers the tombstone; peers see the member as silently absent until an owner removes them manually.
- **A device that has not learned of a removal yet** still accepts the removed key's handshake. Access ends per device as the tombstone reaches it, not at one instant.
- The same founding-owner identity active on two devices can race itself into two concurrent rotations at the same epoch; peers apply whichever rekey entry reaches them first and can temporarily split across the two new rooms until a later rotation or catch-up sync reunites them. (Pre-existing class of race — the same happens when one owner removes members from two devices at once.)

### Script execution

User code runs only as Code Apps: sandboxed, non-same-origin iframes with a nonce-protected postMessage bridge; the CSP blocks external scripts, network, frames, and forms. The visual-era script sandbox (`evaluateScript` / `new Function`) was removed along with `'unsafe-eval'` (2026-08).

**Owner-sealed source** (2026-09-17, `store/sourceSeal.ts`): the source doc rides the member mesh, which applies every update of every member — without more, a viewer on a patched client could replace the app everyone runs, and the new code would act with the OWNER's rights on the owner's device and grant itself network origins through its own manifest. Owners therefore sign the list `path → SHA-256` on every source write (map `seal` in the source doc). A device runs — and reads the manifest for host permissions, channel shares and app roles from — only a snapshot matching a seal signed by an owner (current, or provably an owner until it was removed / left). When the live source does not match: the device keeps running the last version it verified (`held`); after a reload there is nothing to run (`blocked`, explained on screen); owner devices that hold a verified snapshot — the keeper is the always-on one — put it back after a 4 s grace (long enough for another owner's seal to arrive after its write). Once a device has seen a valid seal for a dapp, a missing seal counts as tampering. **A seal survives the loss of its signer** (2026-09-22). From 2026-09-18 to 2026-09-22 the seal was not enforced: dapps whose founder had left carried a seal signed by a key that was no member any more and had no tombstone proving it once was an owner, so every device blocked them. Now every device remembers the last seal it VERIFIED (device-local, through `deviceStore.ts`, so the keeper keeps it in its data directory), and that exact seal stays valid on that device after its signer is gone, because the device checked it while the signer was an owner. A seal signed by a current member without the owner role is tampering, as before. Any owner device re-signs a seal whose signer it cannot vouch for, at most once per 30 s and never a seal it signed itself, which makes the dapp `sealed` for fresh devices again. `SOURCE_SEAL_POLICY.enforce` is `true` again and stays as an emergency switch.

Residuals: a device that never verified a seal for a dapp runs its source on first sight (`legacy`) when there is no seal, or when the seal is validly signed by a key it cannot place (no member, no proof it was an owner). Both give a member on a patched client the same result on such a device: until a remaining owner has re-signed, a fresh joiner can be handed rewritten source. A device that verified a seal once is not affected: for it a missing seal, a changed source or a seal by an unknown key is tampering. A demoted-but-not-removed owner's seal stops counting on devices that did not verify it before, until another owner device re-seals. The code editor edits the live doc and is owner-only. **Owner devices sign only what they verified (2026-09-23).** Until then an owner device "repaired" a seal signed by a key it could not place, or by a member without the owner role, by signing the LIVE files: a member could seal its own rewrite with a throwaway key and the always-on keeper signed it for everyone. Now files a device verified stay approved whatever happens to the seal (and an owner re-signs exactly those files); other content is restored; a device that verified nothing for a dapp signs nothing for it (its source runs as `legacy` there). Restores and re-signs are capped at one per 30 s per dapp. **Seals are bound to their dapp (2026-09-23).** The seal's `dappId` is the signing device's local id — every device picks its own when it joins — so it is only a hint, and comparing it rejected every seal written on another device (the restore loop between keeper and browser that day). The binding is the dapp **genesis** (`store/dappGenesis.ts`): a random id the founder writes once into the dapp doc, signed; only the pinned founder's signature counts, every device pins the first genesis it verifies, and the founder's device puts its record back when it is deleted or replaced. Seals v2 carry the genesis id; a seal for another genesis is tampering, so a member of two dapps that share an owner can no longer replay one dapp's sealed source into the other. Residuals: unbound v1 seals (all seals before 2026-09-23) keep counting on a device until it verified a v2 seal for the dapp — owner devices upgrade them as they open the dapp; dapps whose founder is gone get no genesis and stay unbound; a device's first sight of the genesis is trust-on-first-use, like the member list.

**Sandbox escape hatches closed** (2026-09-17): the iframe has no top-navigation token (a click used to let script replace the host tab with a look-alike and carry data out in the URL). http(s) links go through the `ui.openLink` bridge call — host confirmation showing the full address, then a new tab with `noopener`; addresses with embedded credentials are refused; the host page's `frame-src` stops the frame from navigating itself elsewhere. `webrtc 'block'` closes the path `connect-src` does not cover (Chromium enforces it, Firefox does not — residual). `$store` values are capped (256 KB, plain objects). Every `$share.*` call needs `permissions.host.sharing`, and ending a share asks the person.

### Invites

Invite use accounting now requires owner role. Lobby approval still encrypts room credentials to the invitee's RSA-OAEP public key. Approval logic is centralized in `invites.ts::approveLobbyDevice` (owner-signed member add first, then per-device-encrypted credential grant) and shared by the settings page, the global Requests inbox, and 1-step auto-approval.

**1-step (auto-approve) invites** (2026-08): an owner may flag an invite `autoApprove` at creation. Any online owner device (including the headless keeper) then admits every device that appears in that invite's lobby — owner-signed member add as `editor`/`viewer` (never `owner`), credentials encrypted to the joiner's key as usual — *without* the safety-number ritual. This is an explicit, per-invite opt-out of device verification: possession of the invite link becomes the sole admission check, equivalent in spirit to the direct credential links below but with membership (write access) included and revocation + rotation still working normally. Consequences the owner accepts by creating one: anyone who obtains the link (forwarding, shoulder-surfing, chat logs) joins silently; a flood of joins is possible (each becomes a signed member an owner must remove); MITM-by-invite-secret-holder is not detected because no safety number is compared. The UI labels these invites and states the risk; deleting the invite closes the door for anyone who has not yet joined.

**Rejoin of an existing member** (2026-09-17): a device whose key is already in the members map can wait in an invite lobby again — it lost its copy (deleted it, was left on an old room by a rotation, or is a keeper that dropped a dapp it founded; the founding owner can never be removed, so "remove and re-invite" is impossible there). Owners see it as a rejoin request (`store/lobbyPeers.ts`); approval writes NO member entry (role, name and the founder's entry stay untouched) and only re-sends the current room credentials. Everything a device announces in the lobby is self-asserted, so anyone holding the invite link can claim a member's public key: the grant is therefore encrypted to the `encPublicKey` STORED in that member's signed entry, never to the announced one — an impostor receives ciphertext it cannot read, and a member without a stored key is not offered for rejoin at all. Rejoins are never automatic: 1-step invites and the keeper's operator auto-admit skip them. Residual: an impostor can make a rejoin request appear (and burn one use of the invite if an owner approves it); it gains nothing readable.

**The member list is judged against a verified baseline** (2026-09-18, review item 1.9): the members this device's auth observer accepted are persisted per device and per dapp (`store/memberBaseline.ts` — `localStorage` in the browser, `device-state.json` in the keeper's data directory, because Node's localStorage is a volatile polyfill and the always-on device would otherwise re-trust its list at every boot). The next session starts from that set instead of from the list the local database happens to hold, so a change that differs — an entry a patched build wrote straight into IndexedDB, a mesh push that landed before the first scan — has to be owner-signed like any other change or it is reverted. Rebuilding the list from the pinned founder instead was tried on 2026-09-18 and reverted the same day: member entries are last-writer-wins, so once two owners have edited each other's entry each carries only its latest signer, the two vouch for each other, the original founder signature is no longer in the document, and the rebuild deletes both and everyone they added (it did, on the keeper, to a dapp with three cross-signed owner devices; `memberCrossSigned.test.ts` guards against a repeat). Nothing here ever deletes a member for lack of a chain: a baseline that is missing, unreadable, malformed or too large to store reads as "none", and that means the old behaviour — the list as found. **Residuals:** the FIRST sight of a dapp on a device is still trust-on-first-use (the same footing as the founder pin), so a device whose database was already forged before it ever scanned adopts that state, and so does a device after the dapp was purged and rejoined; the baseline is written on a ~300 ms debounce, so a crash in that window leaves it one change behind (harmless unless the entries it is missing had meanwhile been re-signed by each other, which would cost them a revert until a peer re-delivers them); and anyone with write access to the device's storage can edit or delete the baseline — deleting it only buys back trust-on-first-use.

**An entry that cannot be proved either way is quarantined, never deleted** (2026-09-18): a member entry whose signature is fine but whose SIGNER this device never verified is left in the document and out of the verified set — no role, no mesh access, and its records are left untouched instead of reverted. This is not a hypothetical: entries are last-writer-wins, so two devices that joined while this one was offline and have since renamed each other carry only each other's signature, and the founder's original signature is gone. Deleting them would destroy real members over a gap in ONE device's knowledge and push that deletion to every peer. What is provably wrong is still deleted: no signature, a signature that does not verify, an entry signed by a key this device knows is not an owner, one that signed itself in (only the founder's own entry is legitimately self-signed), a stamp that goes backwards, an entry a tombstone supersedes. A quarantined member is reported (`getQuarantinedMembers`, a line in the sync panel) and resolves the moment an owner this device does verify re-signs the entry — any rename or role change. Residual: such a member is a non-member on that device until then, so the two do not sync directly; a forged pair of entries planted in the local database that sign each other is likewise quarantined — junk in the document, but it grants nothing.

**Membership decisions are order-independent** (2026-09-18): whether a member entry (or a removal) counts is judged from signed, replicated evidence — the signer's verified entry, or its tombstone's proof of what it was (`formerRole` / `formerEntry`) together with the timestamps — not from "is the signer an owner in what this device happens to know right now". Before, two peers that learned of "owner B added X" and "an owner removed B" in opposite orders disagreed for good: one kept X, the other deleted it, the first put it back, a few times a second, for as long as the dapp was open (the doc grew, and the lagging peer's mesh served X full read access). A peer that accepted an entry before it learned of the signer's removal now re-checks it when the tombstone arrives, and a batch that carries a chain (an owner adds a second owner, who adds a member) is resolved in dependency order rather than in map order. Consequence, the same trade-off as for records above: what a removed owner signed BEFORE its removal stays valid — refusing it would throw out every member that owner legitimately added — so a removed owner can backdate an entry to just before `removedAt` and have it accepted. Members it mints with a later stamp are dropped by every peer, including one that had already accepted them.

**Data of former members** (2026-09-17): a record, file or deletion stays valid after its author was removed or left. A member tombstone now carries what the member was — `formerRole` on an owner-signed removal, and the member's own owner-signed entry (`formerEntry`) on a self-signed departure, where a self-asserted role would be worthless. Peers that still know the entry only accept the removal when the embedded proof matches that entry exactly, so a demoted viewer cannot leave with an old "editor" entry. Anything the key signed with a timestamp up to `removedAt` is then accepted from a writer (owner / editor), so a reload or a fresh join no longer deletes that person's data for everyone. Record tombstones whose record is unknown (every tombstone after a reload) are validated on their own signature instead of being deleted. Residual: timestamps are writer-supplied, so a removed editor can get backdated writes accepted through a peer that has not yet learned of the removal (the removal-lag window of the mesh whitelist). Tombstones written before this change carry no proof, and records of a member demoted to viewer are still reverted on a fresh verification — a safe rule for demotion needs more than a timestamp, because the demoted member is still connected and can backdate.

**Signed invites** (2026-09-17): an invite is owner-only state. Entries are owner-signed (`protocolCore.ts` "Invites"), closing is a signed tombstone, and the use cap is the signed `uses` counted against members whose owner-signed entry names the invite (`viaInvite`) — the `usesLeft` field is bookkeeping only. The auth observer verifies every invite from scratch each session; lobbies are opened, and devices approved or auto-approved, for verified invites only. Removing a member (or seeing one leave) closes every invite that existed then — it knows their lobby secrets. Invites written by older builds are unsigned and get deleted; owners create new ones.

**Signed lobby** (2026-09-17): every awareness field in an invite lobby is writable by whoever holds the link. Three things now stand between that and an admission: (1) the announce is signed by the key it names, bound to the lobby (`store/lobbyAnnounce.ts`) — nothing is listed, approved or auto-admitted (keeper operators included) before it verified, so nobody can pair a victim's public key with their own encryption key; (2) the connection code is 8 digits from a PBKDF2 stretch over both device keys and the lobby id (`connectionCode.ts`) — a colliding key has to be brute-forced, slowly, while the victim is waiting; (3) the credential grant is signed over lobby, joiner and exact ciphertext (`store/accessGrant.ts`), and the joiner accepts it only from a device that proved an owner key in that lobby and that the grant names inside. **Evil-twin owner — joiner-side confirmation (2026-09-18):** a link holder can announce ITSELF as an owner (its announce verifies: it really holds that key) and sign a grant into a room it controls; the joiner used to take the first valid grant and leave the lobby at once, so it ended up in a fake copy of the dapp and the owner-side code comparison never happened. Now a grant is HELD (`store/pendingGrant.ts`): the joining device shows "approved by X — connection code N" and uses the grant only after its user confirmed that the approving device shows the same code for it; the approving device puts the code in front of its user once more right after approving (a single-use invite closes with the approval, so its request row disappears; for a multi-use invite the row stays, marked as approved, until the device has joined). Refusing ignores that signer for the rest of the session and keeps the device waiting for the real owner. The held grant survives a reload (still encrypted, in the local-only catalog entry; its signature is checked again). The keeper has nobody to ask: it uses an approval signed by one of its operators (verified owners of its control dapp) at once and holds every other one until an operator sends `confirm-join` / the dashboard's `POST /api/dapps/:id/grant`. Residuals: the comparison is a human step — a user who confirms without looking gains nothing, and the twin's self-chosen name can copy the real one (the dialog says the name proves nothing by showing the code as the thing to check); with a **1-step invite** nobody approves by hand, so no device puts the code in front of a person — it can only be read in an owner's Requests list while the invite is still open; a twin can keep overwriting the joiner's grant entry (denial of service for that join, as any link holder could do before). The code itself is 8 digits from a PBKDF2 stretch — a twin would have to grind a key whose code with the joiner equals the real owner's.

**Founder pin and clocks** (2026-09-17): `config.meta.createdBy` names the one member nobody can remove, but every member can write it — each device pins the first founder it saw (device-local, trust on first use — stored where the verified member baseline is, so the keeper keeps its pins across boots instead of re-taking them from the document), reverts changes and uses the pin for removal checks. Precedence between signed entries is wall-clock based; writers stamp `max(now, what they supersede + 1 ms)` so a device with a slow clock can still remove members and delete records. There is deliberately NO upper bound on accepted timestamps: a verifier with a wrong clock would otherwise delete other people's valid data.

**Verified members everywhere** (2026-09-17): role checks, the mesh whitelist, record scans and rekey validation read the auth observer's verified member set, not the live map — an entry a member wrote a moment ago grants nothing. The mesh forgets refusals when the verified set changes (a freshly approved device dials before the owner's scan has accepted its entry).

### Self-asserted contact names (2026-08)

Contact pairing derives each side's contact-card name from the *peer's own announcement*: the inviter's name travels in the signed lobby announce, the requester's in the signed pairing request. These names are covered by the sender's signature and length-capped at the protocol boundary (`MAX_PEER_DISPLAY_NAME_LENGTH`), but they are **self-asserted, attacker-chosen text** — a name proves nothing about who is on the other end, and anyone can announce themselves as "Mom". The safety number remains the only identity check; the UI renders announced names as plain text only, and the derived name is an editable default (it never overwrites a name the user typed). Approving a pairing request must be based on the expected-requester context plus the safety number, never on the announced name.

### Contacts (2026-09-17)

Pairing proves only that the other side held the invite code. A contact counts as verified once the person marks it so after comparing the safety number over another channel (`setRelationshipVerified`, Contacts page); the share consent dialog warns about unverified contacts. Invite links carry their secret in the URL fragment, which never reaches the hosting server, proxies or link-preview fetchers. **Since 2026-09-18 the number is on both screens before anyone approves** (`pendingPairingSafetyNumber`): the joining device shows it on its pending contact card (it knows the inviter's key from the signed, code-gated announce), and the inviter sees it in the request row next to Approve, derived from the requester's key in the signed request plus the invite's pair context. It is the same number the finished contact carries, so comparing it once — before approving — is enough. Residual: comparing is a human step, and a request carries a self-asserted name that can copy the expected one, which is why the row labels the number, not the name, as the thing to check.

**Channel-room payloads are sealed (2026-09-22, review item 6.5).** A `(relationship, dapp)` channel room is a y-webrtc room: its id + password hand the whole channel doc to anyone holding them. Channel-binding deliveries and acks are now encrypted to the peer's relationship encryption key before they are signed and stored (`channelBindingRuntime.ts`: `hybridEncrypt` — a fresh AES-256-GCM key and 96-bit IV per event, the key wrapped with RSA-OAEP-256; AAD = channel id, the event's random id (the delivery nonce / ack id), stream id, signer key and recipient key). The Ed25519 signature covers the ciphertext and the AAD fields, so authenticity is unchanged, and a ciphertext re-signed by another key or lifted into another event no longer decrypts. Events no longer carry the sender's local `relationshipId` (the channel id takes its place). A leaked channel credential therefore no longer reads queued deliveries, acks or future traffic. Residual: it still sees routing metadata — both relationship signing keys, event and stream ids (which tell deliveries from acks), timestamps, entry sizes and counts — and it can still delete queued entries or stuff the doc (entries are signed, so it cannot forge or alter one; stuffing is bounded per signer by `MAX_STREAM_ENTRIES_PER_SIGNER`). No forward secrecy: whoever later obtains a relationship's encryption private key can read the channel traffic it recorded. **Migration allowance:** writes are always sealed, but plaintext entries written by earlier builds are still read while `CHANNEL_PAYLOAD_POLICY.acceptPlaintext` is `true` — until that flag is flipped to `false` in a later release, a party that can SIGN (the peer) may still send plaintext; a credential holder cannot, so this does not reopen the leak.

### Keeper control dapp (2026-09-17)

Commands are operator-signed records, and the observer accepts any validly signed version of a record — so a command runs once (ids persisted in `executed-commands.json`) and only within 10 minutes of its creation time. The control Code App believes status and command results only when the keeper's key (the pinned founder of the control dapp) signed them, and renders http(s) links only.

## Known limits / residual risk

### Private keys at rest — hardened (2026-08)

Device Ed25519/RSA private keys are now **non-extractable `CryptoKey` objects persisted in IndexedDB** (`src/services/identity.ts`). localStorage holds only public identity metadata. A same-origin XSS can still *use* the keys to sign/decrypt while a tab is open (unavoidable for any in-browser signer), but it can no longer exfiltrate key material for offline, permanent impersonation. Legacy plaintext identities are migrated at startup; the plaintext is destroyed only after a verified IndexedDB round-trip. Identity export was removed by design — non-extractable keys cannot be exported, wrapped or otherwise; multi-device use is per-device keys + invites. Legacy plaintext backup files are still importable (material is moved into non-extractable storage on import).

Residual risk:

- **Relationship identities** (`relationshipIdentity.ts`) still store per-relationship Ed25519 private keys as hex inside the local-only root Yjs doc (IndexedDB-readable JSON). An XSS can exfiltrate those. Moving them to non-extractable keys requires reworking how relationship key material lives in the CRDT — tracked as future work.
- A creation-time persistence failure (rare private-browsing modes) falls back to the legacy plaintext format so the identity is not lost; migration retries every startup.

### Peer whitelist on the member mesh (2026-09-17)

A dapp's data and source documents no longer travel over y-webrtc. y-webrtc admits anyone who knows the room id + password and immediately sends them the whole document; it has no hook to check a peer first. Both documents now sync only over the member mesh (`src/services/blobRoomManager.ts`, the mesh that already carried file content), whose session handshake is the whitelist:

- Both sides exchange `hello` (Ed25519 public key + nonce) and `proof` (signature over both keys and both nonces). A session turns `ready` only when the proven key passes `isTrustedBlobPeer`: a current entry in the signed members map, or — while a fresh joiner's members map is still empty — exactly the owner key named in its encrypted access grant (`grantedBy`, human-verified through the connection code). A device with neither trusts nobody.
- Before `ready`, no document byte is sent or accepted: live updates, state pulls and file chunks are all gated on it (`requireReady`). A refused device is not redialed for 2 minutes (cleared when membership changes).
- When the members map changes, every open session whose key is no longer trusted is dropped at once, so a removed member stops receiving updates as soon as its removal reaches each device.
- Presence shown in the UI is the set of verified sessions, not self-asserted awareness state.

What this replaces: a removed member that kept the room password can still reach the broker room and attempt connections, but every honest device refuses it and it reads nothing — without anyone having to move rooms. That is why automatic credential rotation (below) could be switched off.

Residual risks:
- **Signaling metadata.** The mesh topic and its signaling encryption key derive from the room credentials. A removed member holding them can still decrypt signaling envelopes (WebRTC offers/answers/ICE candidates, i.e. peer IP addresses and online times). Only a credential rotation ends that.
- **A device-chosen signaling server sees that device's metadata** (2026-09-18, Settings → Signaling). A person may point their own device at any `ws(s)://` broker, and the mesh then subscribes every one of that device's dapp topics on it and announces itself there. What such a broker learns is the metadata above: which addresses are online for which (hashed-looking, credential-derived) topic and when, for every dapp open on that device — and it can delay or drop introductions, which looks like "peers not found". What it cannot do is read or forge anything: the signaling payloads are AES-GCM-encrypted under a key derived from the room credentials it does not have, and no document byte moves before the Ed25519 member handshake. The setting is device-local, so one person can only expose their own device's metadata; nothing in a dapp, an invite or a document can point somebody else's device at a broker. The risk to weigh when a *dapp-level* broker list is built (TODO, later steps): an invite that names an attacker's broker would hand it the joiner's presence metadata, which is why the join screen has to show the broker host.
- **Removal lag.** A device keeps serving a removed member until the removal has synced to it. A removed member connected to a device that is partitioned from the owner keeps reading that device's updates until the partition heals.
- **Joiner bootstrap.** Until its members map has synced, a fresh joiner talks only to the granting owner. If that owner goes offline first, the joiner waits for it (other members cannot help, by design — accepting an unverified first document would let any password holder forge the members map).
- **Credentials-only devices** (keeper `addByCredentials`) are not members, so they no longer sync at all; admit the keeper through an invite instead.
- **Mixed builds.** Builds without mesh live sync only receive live changes over y-webrtc, which new builds no longer speak; they still serve and answer state pulls. All devices of a dapp must update.
- **Out of scope:** invite/lobby rooms (the other side is by definition not a member yet; only presence and an encrypted grant are shared there) and relationship pairing/channel rooms keep their own y-webrtc rooms with per-relationship credentials.

### Room password rotation — hardened (2026-08)

> **Automatic rotation is switched off (2026-09-17).** `AUTO_ROTATE_ON_MEMBER_REMOVAL` in `src/services/store/rotationPolicy.ts` is `false`: neither an owner-initiated removal nor a voluntary departure rotates the room any more. In practice the "offline members miss rotations" limit below split a dapp into devices on the old room and devices on the new one. Until rotation can carry offline members along, a removed or departed member keeps the room password: honest peers reject its writes (no longer a signed member), but a device that kept the password can still connect and read new data. The mechanism below is unchanged — explicit `rotateDappCredentials` calls work and every device still follows existing rekey entries — and everything in this document that says removal or departure "rotates" describes the switched-on behavior.

(What follows describes the rotation mechanism itself, which still exists for explicit use and for following earlier rotations.) A rotation (`src/services/store/rotation.ts`) works like this: the owner generates a fresh roomId + password (rotation epoch + 1), encrypts them per remaining member to that member's stored RSA-OAEP `encPublicKey`, and writes owner-signed `rekeys` entries into the doc while still connected to the old room. Every peer runs a rekey observer that applies an entry only if it is addressed to it, Ed25519-signed by a current owner, its epoch strictly exceeds the local room epoch, and the decrypted plaintext's epoch matches the signed envelope (anti-splicing); it then updates its local catalog and reconnects both the main and the derived source provider to the new room. The removed member sees only ciphertexts it cannot decrypt. Lobby grants now carry `roomId:roomPassword:epoch` so newly approved members join at the current epoch.

Residual risk:

- **Offline members miss rotations.** The rekey entry travels with the doc, but after everyone migrates, nobody is left in the old room to sync it to a member who was offline during rotation — they must be re-invited. (Keeping a bridge peer in the old room would leak post-rotation data to the removed member; deliberately not done.)
- **Members added before rotation existed** have no stored `encPublicKey` and cannot be re-keyed; rotation reports them (`skipped`) and the UI tells the owner to re-invite them.
- **Race at removal:** a removed member still connected while the tombstone + rekey entries propagate can read those final updates (ciphertexts only) and any data written in the same instant. Rotation revokes access going forward; it does not un-share previously synced data.
- The `rekeys` map is verify-on-read (forged entries are inert on honest peers) but not covered by the auth observer's revert logic — a malicious writer can delete rekey entries. Connected peers typically apply entries within milliseconds of arrival; offline peers cannot be reached either way.

### Direct credentials (no link form)

Direct `dapp://roomId/password` links were removed (2026-08) with the invite-format unification: every invite is now `dapp://invite/pair/<code>` or `dapp://invite/app/<lobbyId>/<password>`, and both go through their respective approval handshakes. Credentials-only access survives solely as the headless keeper's `addByCredentials` API (agent/tooling path, never reachable from a link or QR); a device added that way can read the room but stays unsigned — every honest peer reverts its writes until an owner admits it through the lobby. Users who want zero-friction joining use a 1-step (`autoApprove`) invite instead, which keeps the owner-signed member add and encrypted credential grant.

### CSP trade-off

`'unsafe-eval'` was removed from `script-src` (2026-08) along with the visual-era script sandbox — neither the host page nor Code Apps may use `eval`/`new Function` (srcdoc iframes inherit this document CSP). `'unsafe-inline'` remains **required**: Code Apps are srcdoc iframes and inherit the host CSP, so inline `<script>` in user apps only runs because of it. Dropping it would need Code Apps served from a genuinely separate origin — a larger architectural change.

## Manual adversarial checks

Before merging security-sensitive changes:

1. Editor tries to set own member role to owner → restored.
2. Editor injects forged record signed as another member → reverted.
3. Editor injects forged record signed as local public key → reverted.
4. Viewer tries record write → rejected/reverted.
5. Owner removes a member → membership tombstone accepted; old signed add replay rejected.
6. Owner removes a member → every other device refuses the removed key's mesh handshake and drops its open session once the tombstone has synced; the removed device receives no further document data although it still holds the room password. (No rotation happens; an explicit `rotateDappCredentials` still moves everyone that is online.)
7. Rekey entry signed by an editor (or with a spliced/replayed epoch) → ignored by honest peers.
8. Direct credential join shows informed-consent warning.
